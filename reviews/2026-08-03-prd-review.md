# PRD 完整度与业界最佳实践评审

- 评审日期：2026-08-03
- 评审对象：`docs/2026-02-27-decision-engine-saas-design.md`
- 评审目标：判断产品需求是否足以支撑下一阶段工程开发，并从 SaaS 产品完整度、实时决策产品实践、安全治理与可验收性角度给出完善建议。

## 1. 结论

现有 PRD 的优势是业务方向清晰、控制台交互细节丰富、版本发布治理意识较强，并且已经收敛出一个合理的 P0 垂直切片。但它目前更像“产品方案 + 交互规格 + 节点运行语义 + 治理规则 + 部分技术约束”的合订本，还不是一份可以直接驱动多团队并行实现和验收的工程级产品基线。

推荐结论：

> **P0 可以进入基础工程与技术验证，但核心业务实现前应先补齐需求可追踪性、核心运行契约、外部 API、Counter 数据来源、环境隔离、副作用安全和生产验收标准。完整 MVP 暂不建议直接并行开发。**

## 2. 当前文档做得较好的部分

1. **P0 垂直切片明确。** 以注册防刷样板贯通资源准备、编排、验证、版本、申请、发布、运行和审计，比按页面横向铺开更利于尽早验证产品价值。
2. **治理对象初步清晰。** Draft、不可变版本、发布申请、审批记录和环境当前生效版本的区分是正确的产品基础。
3. **编辑器交互描述充分。** 三栏编辑器、变量 token、节点验证、整流测试、问题面板和版本 Diff 已达到可继续做详细设计的程度。
4. **资源治理意识较强。** 资源指纹、受保护资源、凭据版本、API Key 轮换、高风险能力和审计均已被纳入产品范围。
5. **明确了一部分非目标。** 实时监控页面、请求回放、灰度实验和生态能力被后置，有助于控制首发范围。

### 3.2 用户、SaaS 生命周期与产品完整度

现有角色主要覆盖策略师、研发协作者和审批人，尚缺完整 SaaS 产品所需的角色与生命周期。

需要补充的角色至少包括：

- 租户管理员：创建租户、邀请成员、停用成员、配置安全策略和管理配额。
- 接入开发者：申请/轮换调用凭据、阅读 API 契约、进行联调和处理错误。
- 安全与审计人员：审查权限、导出或留存证据、处理异常访问。
- 运维/on-call：处理发布故障、依赖故障、容量和数据恢复。
- 客户支持或平台运营：处理账号、配额、租户停用和数据请求。

| ID | 优先级 | 缺口 | 完善建议 |
| --- | --- | --- | --- |

| PRD-M05 | P0 必须 | 未定义 API 接入开发者的 onboarding | 增加基础地址、环境、示例、错误码、请求追踪、限流、调试和凭据轮换旅程 |

| PRD-P102 | P1 | 未定义租户停用、数据导出、删除、恢复和合规请求 | 增加租户生命周期和数据主体/客户数据处理流程 |

### 3.3 成功指标与非功能目标不可验收

当前仅有“策略发布时间从天级降至小时/分钟级”“SLA >= 99.9%”“p95 < 200ms”等方向性描述，缺少基线、统计口径、流量模型和责任人。

建议将每个指标写成以下格式：

`指标名称 / 业务目的 / 计算公式 / 数据来源 / 统计窗口 / 分位与维度 / 基线 / P0 目标 / MVP 目标 / Guardrail / Owner`

P0 至少应确定：

1. 决策 API 可用性、错误预算、p50/p95/p99 延迟。
2. 目标 QPS、峰值倍数、并发、请求体大小、最大节点数、最大产物大小。
3. 单租户与全站限流、队列积压和依赖超时预算。
4. 发布成功率、发布生效时间、回滚恢复时间。
5. 执行日志接受的最大丢失率和最大落库延迟。
6. RPO、RTO、备份恢复验证频率。
7. 策略师从创建空白流程到 Test 生效的完成率和中位用时。
8. 编辑冲突、自动保存失败和校验失败的可恢复性指标。

| ID | 优先级 | 问题 | 完善建议 |
| --- | --- | --- | --- |
| PRD-B03 | P0 阻塞 | 无容量基线和可执行的性能验收模型 | 在开发前冻结 P0 流量画像与压测场景；延迟必须说明是否包含画像查询和 Redis 网络耗时 |
| PRD-M06 | P0 必须 | 无可用性故障定义和错误预算 | 明确哪些响应计入可用性、依赖降级如何计数、计划维护是否排除 |
| PRD-M07 | P0 必须 | 无发布/回滚和数据恢复目标 | 为发布切换、故障检测、回滚、缓存恢复和数据恢复定义目标 |

### 3.4 图模型和执行语义仍有空白

| ID | 优先级 | 问题 | 影响与建议 |
| --- | --- | --- | --- |
| PRD-B04 | P0 阻塞 | 图语法没有完整定义：多前驱、汇合、分支后合并、最大深度、最大节点/边数和执行顺序不明确 | 单独定义合法图模型；P0 若只允许 DAG 且不允许合流，应明确限制；若允许合流，必须定义变量合并和节点触发条件 |
| PRD-B05 | P0 阻塞 | 缺少端到端 deadline、取消传播、节点预算分配和超时后的终止规则 | 定义请求级 deadline、节点级最大耗时、剩余预算传播、客户端断开行为和外呼取消 |
| PRD-M08 | P0 必须 | “异常策略”是通用字段，但可选策略和各节点默认值未统一列出 | 建立错误分类和策略矩阵，例如 `fail / fallback / continue-with-null / retry / terminate-with-system-error`，禁止节点各自发明语义 |

| PRD-M10 | P0 必须 | `Fixed` 模式“输入什么就是什么”与字段类型校验之间存在冲突 | Fixed 必须按目标类型编辑和序列化，不能把数字、布尔、null、对象全部当字符串 |
| PRD-M11 | P0 必须 | Draft 自动保存只有 debounce 描述，没有并发编辑、revision 冲突和恢复语义 | 定义乐观锁、冲突提示、覆盖规则、断网重试、草稿恢复和多标签页行为 |

### 3.5 核心节点契约中的关键问题

#### Counter 缺少数据生产路径

PRD 将 Counter 定义为“只查询历史窗口统计，不把当前请求写入计数器”，但没有定义任何事件采集、计数写入或外部导入接口。这样 P0 的历史统计值无法由系统产生，是直接的功能闭环缺口。

**建议：** 在以下方案中明确选择一个，并形成独立产品契约：

1. 决策执行成功后由平台异步写入预定义计数事件；
2. 提供独立 Event Ingestion API，由客户业务事件驱动计数；
3. Counter 节点支持显式 `query-and-increment`，并定义原子性和重复请求语义；
4. P0 使用预置模拟数据，仅作为演示能力，并将生产 Counter 移出 P0。

无论选择哪种方案，都必须定义事件时间/处理时间、去重键、迟到事件、窗口边界、时钟、热点 key、精确/近似统计和数据保留。

#### 名单环境与副作用冲突

名单数据被定义为全环境共享，而 Dev/Test 的整流测试与 List 写操作又允许真实副作用。这意味着一次测试可能直接改变 Prod 使用的名单。

**建议：** 默认采用环境隔离的数据平面；确需共享时必须显式创建“跨环境共享名单”，并对 Dev/Test 写操作默认禁止或要求受控临时副本。P0 主线只开放 `query` 是合理的，应把写操作延后到副作用专项设计完成后。

#### Decision Table 无命中默认全 null

在实时反欺诈场景中，“无规则命中即所有输出为 null”容易被错误映射为放行，属于不安全默认值。

**建议：** 强制选择无命中策略：显式兜底行、返回配置错误、固定默认输出，或按流级设置 fail-open/fail-closed。Prod 发布门禁应禁止未声明默认策略。

#### HTTP 动态输出 Schema 不稳定

以下游“最近一次成功执行观察到的 body 字段”作为可引用字段来源，会把偶然样例变成生产契约。供应商响应差异或样例覆盖不足会造成隐藏的运行时 null。

**建议：** HTTP 连接器或节点必须声明 JSON Schema/OpenAPI 响应契约；观察到的样例只用于提示和诊断。Schema 演进需要兼容性检查和 Diff。

#### Function 输出依赖最近一次运行推断

Function 不预声明完整输出 Schema，而依赖最近一次成功运行生成变量树，会产生同样的不稳定契约问题。对生产版本建议强制声明输出 Schema；若暂不实现，应将 Function 标为 P1 实验能力，不阻塞 P0。

#### Response 多返回结构没有判别字段

多个返回结构仅作为内部元数据而不要求对外 discriminator，客户端难以稳定解析。

**建议：** 多结构采用 JSON Schema `oneOf` 配合明确 discriminator，例如 `result_type`；或者 P0/MVP 仅支持单一返回结构。

| ID | 优先级 | 节点问题 | 完善建议 |
| --- | --- | --- | --- |
| PRD-B06 | P0 阻塞 | Counter 没有历史数据写入来源 | 冻结事件生产模型和重复处理语义 |
| PRD-B07 | P0 阻塞 | 名单全环境共享与测试真实副作用冲突 | 默认环境隔离；P0 只读；共享能力显式高风险化 |
| PRD-M12 | P0 必须 | Decision Table 无命中全 null | 强制明确默认策略，Prod 禁止隐式无结果 |
| PRD-M13 | P0 必须 | Profile Query 原始 payload 可能随供应商漂移 | 平台适配器输出应有版本化 Schema；字段目录变化需兼容策略 |
| PRD-P105 | P1 | HTTP 输出通过样例推断 | 改为声明式 Schema，样例只做辅助 |

### 3.6 外部决策 API 产品契约不足

当前 PRD 仅说明 HTTP API、环境级 API Key、`flow_id` 和环境路由，尚不足以让接入方实现稳定客户端。

P0 应以版本化 OpenAPI 文档定义：

- 路径、HTTP 方法、`flow_id` 的位置及编码规则。
- 请求 Schema、额外字段策略、最大 body、压缩和 Content-Type。
- 同步超时、客户端 deadline、重试安全性和幂等键。
- 成功响应、业务拒绝结果、校验错误、系统错误和依赖降级的边界。
- HTTP 状态码和统一机器可读错误，推荐采用 RFC 9457 Problem Details。
- `request_id`/`trace_id`、服务版本和实际执行版本的响应头或响应字段。
- 限流算法、响应头、配额和 429 行为。
- API 版本、兼容、废弃和迁移策略。
- SDK/示例、契约测试和沙箱联调方式。

#### API Key 作用域过大

环境级 Key 可调用该环境下所有 flow，且不绑定调用应用或 flow 白名单，泄露后的爆炸半径过大，也无法按调用方做限流和审计。

**建议：** 将接入主体建模为 `Client/Application Principal`，Key 至少绑定 tenant、environment、client，并可配置 flow scopes。限流、审计、撤销和轮换都以 client 为维度。

#### Key 轮换不是真正无中断

“备用 Key 提升后原当前 Key 自动停用”不能支持客户端分批切换。

**建议：** 支持明确的 overlap/grace period：创建新 Key、双 Key 同时有效、观察使用情况、到期或人工撤销旧 Key。只保存 hash，完整 Key 默认仅创建时显示一次。若业务坚持可再次复制，需采用强制重新认证、break-glass、严格审计和 KMS。

| ID | 优先级 | 问题 | 完善建议 |
| --- | --- | --- | --- |
| PRD-B08 | P0 阻塞 | 外部 API 没有可实现契约 | 先交付版本化 OpenAPI 和错误目录，再实现服务 |
| PRD-B09 | P0 阻塞 | 环境级 Key 可访问所有 flow | 引入调用应用主体和 flow scope |
| PRD-M14 | P0 必须 | Key 轮换立即停用旧 Key | 支持重叠有效期、使用观测和显式撤销 |

### 3.7 测试、证据与副作用安全

PRD 将节点验证和整流测试结果限制在当前会话，且 Dev/Test 默认真实执行 HTTP、Notify 和名单写操作。这对高风险决策平台不足以支撑安全审批。

建议引入三种执行模式：

1. **Preview**：纯计算或使用 fixture/mock，不产生外部副作用。
2. **Sandbox Test**：使用环境隔离资源，允许受控副作用并保留可分享证据。
3. **Live Test**：显式高风险操作，二次确认、配额限制、完整审计。

版本生成和 Prod 申请应关联不可变测试摘要，包括测试用例版本、输入摘要、执行版本、资源指纹、结果、时间和操作者。敏感输入保存前必须按字段分类和脱敏策略处理。

| ID | 优先级 | 问题 | 完善建议 |
| --- | --- | --- | --- |
| PRD-B10 | P0 阻塞 | 测试真实副作用缺少环境隔离和明确模式 | P0 仅允许只读主线；P1 前完成 Preview/Sandbox/Live 设计 |
| PRD-M16 | P0 必须 | 测试结果会话级，不可作为审批证据 | 保存版本关联的脱敏测试摘要和结果 hash |
| PRD-M17 | P0 必须 | 缺少测试样例集合、断言和回归套件 | 每个 flow 支持版本化测试用例与预期结果，P0 至少后端支持 |

### 3.8 发布、审批和回滚治理

1. 同一人可同时具备审批和发布权限并完成 Prod 全流程。对于风险决策产品，应提供可配置的“四眼原则”和禁止自审批。
2. 回滚只切换决策流版本，无法回滚已轮换凭据、可变名单数据或已经发生的外部副作用。PRD 需要明确“配置回滚”不是“状态回滚”。
3. 发布申请、批准、发布、失败、重试、撤销和回滚状态尚未用正式状态机定义，并发申请和并发发布行为不清楚。
4. 资源被当前 Test/Prod 引用才进入保护状态，但历史可回滚版本依赖的资源同样需要可恢复或可解析。

| ID | 优先级 | 问题 | 完善建议 |
| --- | --- | --- | --- |
| PRD-B11 | P0 阻塞 | 发布与审批状态机、并发和幂等语义未冻结 | 给出合法状态、事件、操作者、前置条件、终态和重复请求行为 |
| PRD-M18 | P0 必须 | 回滚范围表述过宽 | 明确仅回滚版本指针；列出不回滚项和后续补偿手段 |
| PRD-M19 | P0 必须 | Prod 缺少可配置职责分离 | 支持禁止申请人审批、禁止同人审批与发布、紧急 break-glass |
| PRD-M20 | P0 必须 | 历史稳定版本所依赖资源的可恢复性不明确 | 资源内部 revision 和历史解析必须满足回滚窗口 |

### 3.9 数据、安全、隐私与审计存在冲突

#### `rawRequest` 与敏感数据原则冲突

Request 节点描述 `rawRequest` 保留完整原始入参用于离线分析和审计，而日志章节又声明完整敏感请求体默认不写入日志。应避免把原始输入默认长期保存。

**建议：** 建立数据分类和字段级处理策略：

- 默认不落原始请求；只在明确配置、合法依据和限定时长下采样保存。
- 支持字段 allowlist、mask、hash、truncate、drop。
- 指定日志、审计、测试证据、ClickHouse 和备份的独立留存期。
- 支持租户级删除和数据导出。

#### 审计“不可篡改”未定义

普通数据库表的“禁止 UI 编辑”不等于防篡改。产品要求应明确最小保障：append-only 权限、事件 hash 链或签名、独立存储/周期导出、保留和校验机制。

| ID | 优先级 | 问题 | 完善建议 |
| --- | --- | --- | --- |
| PRD-B12 | P0 阻塞 | 原始请求保留和日志脱敏口径冲突 | 冻结数据分类、默认落盘策略、留存和删除规则 |
| PRD-M21 | P0 必须 | 审计不可篡改缺少可验收定义 | 定义 append-only、完整性校验、访问控制和保留期 |
| PRD-M22 | P0 必须 | 缺少安全验收基线 | 选定 OWASP ASVS 级别/适用条目，并映射到安全测试 |
| PRD-P108 | P1 | 缺少隐私、数据驻留和跨境说明 | 商业发布前形成数据处理与区域策略 |

## 6. P0 最小验收清单建议

以下内容应转化为可自动化或可复核的验收项：

1. 租户 A 的用户、资源、Draft、版本、日志和 Key 不能访问租户 B 数据。
2. 两个编辑会话同时修改同一 Draft 时，系统能够检测 revision 冲突，不静默覆盖。
3. 核心六节点的输入、输出、错误、null/absence 和超时行为有固定 fixture。
4. Counter 能通过已选定的数据生产路径获得确定性历史值。
5. P0 名单查询不会因 Dev/Test 操作修改 Prod 数据。
6. Draft 通过确定性编译产生相同 canonical artifact hash。
7. Test 发布申请重复提交、重复批准和重复发布不会产生多个有效切换。
8. 发布时资源指纹变化会阻止上线，提示内容可定位资源和变化。
9. 指针切换后所有 executor 实例在约定窗口内加载同一产物；旧实例和冷启动行为可验证。
10. 回滚只恢复版本指针，并明确显示不包含名单、凭据和外部副作用。
11. API Key 只能访问授权 environment/client/flow，撤销在约定窗口内生效。
12. 外部 API 的所有错误符合统一错误契约，并包含 request/trace ID。
13. 日志投递失败不阻塞决策响应，但不会无声丢失；达到丢失预算时告警。
14. 请求和节点日志按字段策略脱敏；禁止凭据、Key 和未授权原文进入日志。
15. 在目标 QPS、产物大小、节点数和依赖延迟下满足 p95/p99 与错误率目标。
16. PostgreSQL、Redis、日志系统或画像依赖故障时的响应、降级和告警符合矩阵。
17. Test 当前版本可在执行实例重启和缓存丢失后恢复。
18. 关键写操作均有操作者、租户、request ID、对象 revision、结果和失败原因审计。
19. 密钥轮换支持双 Key 重叠窗口并能观测旧 Key 使用情况。
20. P0 端到端流程具备一组成功、拒绝、无命中、画像降级、名单未命中、超时和非法输入用例。
